Three Open Problems

Exploratory plans for gaiting, for reinforcement-learning throughput and universality, and for fingertip co-design — in the order they were prioritised, with what each one costs and what would make it stop.

Problem 1highest priority · partly executed today

Gaiting and screwing from the reoriented shaft

Rotate the tool about its own axis, indefinitely, once it is standing vertical. This was catalogued as the lowest-priority backlog item because gaiting means breaking and remaking contact and every reorientation result in the program depends on a fixed contact set. Standing the tool on the ground is what changes that: a released shaft no longer falls, so the release stops being the expensive part.

Status. The core question is answered. An open-loop four-phase set-point cycle turns a ground-supported shaft 4.99 revolutions in 40 cycles on rv05_manual, 3/3, at 0.5° of final tilt; deleting the floor after the grasp is set loses it in the first cycle on every hand that grips. The operating window, the design criterion and the gear ratio are measured. What follows is the work that remains.
  1. G1Chain it to the carry's real end stateCPU, ~1 h

    The gait currently starts from a shaft placed upright under the hand. The raised-pivot carry produces a vertical shaft at cos 0.996 and 0.113 m, but its end state is a distribution and the schedule is chaotic at the 1e-6 level — re-serialising a keyframe once moved a cell from 0.996 held to 0.783 dropped. Sample the carry's end state over n = 32, set the palm down onto the floor from each one, and run the gait from what actually arrives.

    Kill if the carry's end-state spread in tilt and lateral offset falls outside the gait's measured window (tilt under ~14°, press −6 to +6 mm). Then the seam needs a settling move, not a chained demo.

  2. G2Screen the hand pool on release reachabilityseconds per hand

    The gait's design criterion is whether a hand can withdraw its pads at the far end of the stroke, and it is not the grasp's criterion: rv04_mid solves the gripping ring to 1.78 mm, holds for 40 cycles, and nets 2.2°/cycle because it cannot let go. This is one IK table per hand with no rollout at all, so it can run over the whole Sobol pool rather than the ten CEM hands.

    Kill if release residual does not separate hands on delivered rotation out of sample — it is a clean monotone relation at n = 4 here, which is not evidence.

  3. G3Put a real load on itCPU, ~2 h

    The present load is rim friction against a plane, 0.0072 N·m. A fastener resists with a torque that rises as it seats. Add a torsional load at the shaft tip and sweep it to the stall point; report stall torque per hand, and whether stalling is a slip at the pads or a tip-over.

    The number that matters is stall torque against the 1–3 N bench grip window. Kill if stall arrives below any torque a real driver needs, because then the gait is a demonstration and not a capability.

  4. G4Export and gate for the bench1 session

    A gait plan is a longer set-point list than a carry plan and structurally identical, so the existing export, trajectory-clearance and servo-limit gates apply unchanged. Forty cycles at 50 Hz is about ninety seconds of bus time.

    Watch the servo overload protection: it already fires on 42% of middle-yaw bench runs, and sustained cyclic loading is exactly what it exists for. Log temperature per run. Kill if the per-joint travel this schedule needs exceeds the family's ~1.34 rad clip ceiling — that is a check, not a rollout.

  5. G5Close the loop — and this is the one task where that is possiblesee Problem 2

    The AprilTag rig reads in-plane rotation of a vane about the pinch axis at 0.017–0.33° rms. For gaiting, that sensor measures the controlled variable itself — which has never been true in this program before, and is why the observation-transfer work kept stalling on a policy that ignores its observations. Slip per cycle is directly observable, so a controller can correct stroke and grip against it.

    Do not start this before G3. Without a resisting load there is nothing for feedback to reject and it will distil into a step-index lookup, exactly as the reorient distillation would have.

Problem 2second priority

Faster and better policy training

Two complaints are bundled here and they have different answers. Per-seed variance killing significance is a real, measured problem. Slow training is largely not: throughput is spent, and the honest recommendation is to stop looking for it.

What is already measured, and should not be re-derived. ~10,000 env-steps/s, flat in num_envs (1024 → 3072 buys 5%). The PPO update is 1.1% of wall clock, so no learning-side knob can matter. CUDA graph capture is on; the solver is already at 10/20 iterations, not the 100/50 the scene XML claims. What is left — elliptic→pyramidal cone, fewer line-search iterations, a larger timestep — changes contact dynamics, which is the one thing in this program not to touch.
  1. R1Stop paying for throughput; cut the budget insteadtrainer-side, ~1 day

    b33's own 20M-timestep run converged at iteration 26 of 271: target-axis alignment 55.9 at it26 against 60.5 at it270. Ninety per cent of every run in this lineage is wasted, and warmstarted finetunes settle sooner still. Add a plateau detector on the deterministic held-cos — never the reward sum, which is sign-blind and timing-blind — evaluated every N iterations, and stop on it.

    Expected payoff is 3–8× more arms per GPU-day, which is larger than any throughput lever available. Kill if the plateau detector fires before the trajectory-health scorecard is clean, i.e. if held-cos plateaus while a finger is still idle or the object is de-centring.

  2. R2Decompose the variance before buying seeds~1 GPU-day

    The n needed per design is currently guessed from two incompatible numbers. Warmstarted draws have between-draw sd 0.032 against 0.080 of rollout noise, so ~2 seeds resolve a 0.1 difference. From-scratch draws have sd 0.3–0.5, which is where the n = 48 costing came from. Whether the small band survives a per-design from-scratch Policy A is untested, and it is the number that sets the price of every design search this program might run.

    Kill if per-design from-scratch sd comes back at 0.3–0.5: then per-design RL evaluation is unaffordable and design ranking has to move to open-loop screens — which the gaiting and carry results suggest it can.

  3. R3Use the open-loop controllers as the prior~2 GPU-days

    The reason from-scratch reorient variance is 0.3–0.5 is that the reward is a hard-exploration target and the seed's early exploration decides the run. The program now has open-loop kinematic controllers that solve both the reorient (cos 0.996) and the gait (0.89 of slip-free transmission) on the hardware model, and they are cheap to evaluate at any design. Behaviour-clone from those, then finetune. That removes the exploration lottery at its source rather than averaging over it.

    Kill if the cloned policy inherits the open-loop schedule's brittleness under jitter — which is the specific failure that has to be tested for, since b33 already replays as a step-index lookup and 5 mm of spawn jitter drops it from 0.97 to 0.41.

  4. R4Define what "universal" would have to beatanalysis

    The incumbent is not a weak baseline. A recorded open-loop primitive retargets across topologies — the perp reorient primitive executed on rv03 gives held cos 0.848 — while a trained policy does not transfer even across proximal length. A learned controller earns its place only on a task an open-loop trajectory provably cannot solve. Two candidates exist: spawn jitter, and the unknown fastener torque of G3. The second is better, because the disturbance is persistent rather than an initial condition, and because the bench can actually measure it.

    State the win condition before training anything: policy beats the retargeted open-loop schedule, on the same hands, under the same disturbance, at n ≥ 2 seeds. Anything less is not evidence that learning was needed.

Problem 3third priority

Fingertip shape and co-design

The brief's own framing was that there is no obvious meaningful attack and that sim-to-real is hardest here. Both remain true, but the gaiting result opened one axis that is now quantitative, and it is worth separating that from the parts that are not.

What became decidable today. In a gait, the pad radius is the gear ratio: (r_obj + r_pad − squeeze) / r_obj. Measured across six radii on a fixed hand, delivered rotation tracks that ceiling to 13 mm (52.6°/cycle against the shipped pad's 45.0) and falls away beyond it as the ring leaves the fingers' workspace. The reorientation work, on the same hand and tool, found the opposite: compact convex point contact won every comparison and the radius optimum was 5–6 mm, because that task is a roll and a patch that resists rolling destroys it.

  1. F1Run the two-task Pareto over pad radiusCPU, ~1 h

    One axis, two tasks, one hand, one object. The gait arm exists and costs 40 seconds; the reorient arm reuses the existing fingertip sweep and mutator. Report both metrics against radius on one chart and let the trade be visible rather than argued.

    Obey the trap that voided six of eight candidates in the earlier sweep: tip shapes must be reach-normalised or they sit inside the distal capsule and never touch the object, and geometry edits must pin body inertials or a shape change is a silent mass change. Kill if the two optima turn out not to conflict — then there is no co-design problem here, only a part number.

  2. F2Make compliance a specification, not a sweepbench, 1 session

    The useful output of the sim is not an optimal pad; it is the tolerance band a pad must sit inside. Compliance already has one from the reorient work. Give the gait one too, by sweeping contact stiffness and reporting where transmission and retention break, and hand both to whoever specifies the TPU.

    This is the honest form of the fingertip problem. Do not present a simulated optimum as a design recommendation when the axis that dominates real contact is one the simulator does not model.

  3. F3Print two radii and measure thembench

    The shipped 10.55 mm pad and a 13 mm pad, on the same hand, running the same exported gait plan. Rotation per cycle is measurable on the tag rig to well under a degree, so the predicted 17% difference is far above the measurement floor. This is the cheapest sim-to-real check the program has available, because the prediction is kinematic rather than dynamic.

    If the measured ratio does not move with pad radius, the sim's contact model is wrong in a way that invalidates the gait study, not just this comparison.

Sequencing

G1 and G2 are cheap and unlock the rest; G3 defines whether any of this is a capability, and it is also the disturbance that makes Problem 2's learned controller worth training and the load that makes Problem 3's pad radius worth optimising. R1 is independent of everything and pays for itself immediately. F1 is an hour and should be run alongside G2 rather than scheduled.

The one thing to avoid is the pattern that has cost this program most: launching a policy study against a variable that an open-loop probe would have resolved for free.
