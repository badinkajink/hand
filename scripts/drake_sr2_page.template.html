Hand planning and morphology optimization in Drake

A Drake planning port is feasible. The existing real_v1 geometry supports fixed-hand IK and joint morphology/posture optimization after a small, explicit MJCF adaptation.

The three fixed morphologies were tested as both a nine-position frozen model and a fifteen-position model with six locked gantry coordinates. A seventh solve chose morphology and posture together; freezing its resulting morphology reproduced its fingertip targets. These are reachable, nearby synthetic targets, with warm starts. They establish integration, not manipulation success or a global morphology optimum.

Recommended architecture

Keep the measured geometry and existing morphology records as the source of truth. Add Drake as a planning and design-optimization component alongside the current MuJoCo evaluation pipeline. The prototype reads the existing MJCF and resolves actuator defaults with MuJoCo; it does not duplicate the CAD dimensions.

For a trajectory or several task poses, share one six-coordinate morphology across all knots/tasks and optimize the nine finger angles at each knot. Otherwise an optimizer can improve its objective by changing the hand during a task intended to use a fixed morphology. Generic mathematical programs do not automatically inherit the IK constructor’s locked-coordinate constraints.

m = [x_T, y_T, x_I, y_I, x_M, y_M]             # mount-relative meters
q_k = [yaw_T, mcp_T, pip_T, ...]                # radians, at task knot k
minimize  Σ_k task_cost(FK(m, q_k)) + motion_cost(q) + design_cost(m)
subject to workspace bounds, hardware ROM, collision clearance,
           task/contact conditions, and the same m at every knot

A practical next stage is fixed-morphology kinematic trajectory optimization, followed by dense path-clearance checks and MuJoCo rollouts. That class is documented by Drake; trajectory optimization itself was not implemented in this study. Grasp-force feasibility needs additional contact and force constraints. A fingertip-position solution alone does not certify a grasp.

What must be added before using planned motions

  1. Use the bench limits and current plant calibration. The tested source has nominal ±85° yaw and up to 92° flexion, while the driver caps yaw at ±70° and some flexion joints are tighter. For example, index MCP ends at 64.75°. Preserve the sign/unit conversion in manta_hand/plan.py and measured ranges in servos.py.
  2. Port the intended geometry variant and collision policy. This spike uses the capsule/sphere source, not deployed flat-pad variants, rail/carriage geometry, an object, the table, or a UR5e. Its 21 source exclusion declarations intentionally omit some self-contact. A “collision-free” result refers only to enabled pairs in this simplified hand. Preserve the source gate’s physical intent when adding missing shapes.
  3. Connect fixed-morphology planning to the existing evaluator. Import chosen design records, solve task targets with hardware limits, optimize a motion path, export the named-joint trajectory, then use existing MuJoCo clearance/retention/perturbation checks and plan export. Compare D1–D8 only after matching pad shape, source plant and initialization.
  4. Introduce contact optimization separately. Drake’s hydroelastic contact is worth testing for distributed pad contact. It requires physical calibration and does not reproduce MuJoCo rolling/torsional coefficients merely by selecting a solver. At least one compliant hydroelastic participant is needed for a hydroelastic contact pair.
  5. Keep dynamics claims calibrated. The prototype preserves shipped finger kp=30, kv=0.5 and a 10 N·m cap for conversion checks. The repository’s later calibrated chain uses kp=0.5, kv=0.02 and a 0.35 N·m cap. Gantry damping=2000 with kp=30 is also a simulation placeholder, not measured stepper behavior. In a separate 0.2 s unlocked rollout, maximum travel was only {{GANTRY_MOVE}} mm.

The current backend factory and RL stack are MuJoCo/Warp-oriented. This study does not make Drake a drop-in backend, preserve MJX/GPU batch throughput, or validate contact derivatives. The useful first deliverable is a planning interface that accepts a morphology, task targets and limits, and returns named-joint trajectories plus feasibility diagnostics.

The project environment and lockfile are unchanged. Drake was installed into a separate ignored environment under logs/20261001-drake-port/venv. It ran on this Ubuntu 22.04 host; that local success does not establish official support. Check the current supported configurations before choosing a deployment host.
